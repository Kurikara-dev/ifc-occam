# IFC Occam

[English](README.md) | **日本語**

[![CI](https://github.com/Kurikara-dev/ifc-occam/actions/workflows/ci.yml/badge.svg)](https://github.com/Kurikara-dev/ifc-occam/actions/workflows/ci.yml)

巨大化した IFC (ISO 16739) を、普通の BIM ツールで開けるサイズまで削るためのツールです。何を消すかは IFC クラス単位で人間が決めます。元ファイルは書き換えません。

![間引きでトーラスの三角形数を段階的に落とした図。形の輪郭は残る](docs/images/decimate-steps.png)

*間引き(decimate)を段階的に掛けた例。三角形数を落としても、どこに何があるかは読み取れます。この「読めるところまで削る」がこのツールのやることです。*

> 先に断っておきます。このツールが出力するのは**参照用の派生ファイル**で、設計や施工の正本にはなりません。消した要素は出力から戻りません。判断は必ず元ファイルで行ってください。詳しくは[免責](#免責)に書きました。

**コマンド操作をせずに使いたい方は [クイックスタート](docs/quickstart.md) へ。** [Releases](https://github.com/Kurikara-dev/ifc-occam/releases/latest) の zip をダウンロードしてダブルクリックするだけの手順を、順を追って説明しています。以下の README は開発者向けです。

## 何のためのツールか

鉄骨のような細かい部材を持つワークフローから出てくる IFC は、ボルトや溶接や小さな金物が積み上がって、1モデルで数百MBから数GBに達します。この規模になると汎用の BIM ツールは開くのに失敗するか、開いても実用的な速度で動きません。

この状態のモデルを要素ごとに見ていくのは無理があります。現実的なのはクラス単位で決めることです。どの IFC クラスが要素数と三角形数を食っているかをランキングで見て、ファスナは全部消す、プレートは全部 bbox にする、という粗い判断を下していきます。何千回の個別判断が、数回の方針決めに変わります。

実測した例を1つ。102MB、要素数11,273、三角形数223万の設備モデルで、金物クラス1つ (2,728要素) を削除し、継手クラス1つ (1,784要素) を bbox に落としたところ、78MB、三角形数143万の出力が得られました。**三角形数は36%減、バイト数は24%減**で、dangling 参照はゼロ、新規の幾何生成エラーもゼロでした。ビューアが扱えるかどうかを決めるのは、バイト数より三角形数の方です。

バイト数がどれだけ減るかは、モデルとどのクラスを触るかに大きく依存します。21.5MBの別の設備モデルで、配管継手305要素を凸包(共有形状にも波及させて)に軽量化したところ、17.5MBの出力が得られました。**18.7%減**で、この例でも dangling 参照はゼロ、かつ簡略化した要素の色情報もすべて維持されていました。

## 動かす前に

| | |
|---|---|
| 入力 | `.ifc` (STEP形式)。IFC4 と IFC2X3 でテストしています |
| 出力 | 新しい `.ifc` ファイル (CUI の既定の名前は `<入力名>_light.ifc`)。入力ファイルには一切書き込みません |
| 動作環境 | Windows で開発・テストしています。Python コード自体に OS 依存はありませんが、起動用の `.bat` は Windows 専用です |
| Python | 3.11 以降 |
| 位置づけ | 出力は参照用の派生ファイルです。正本として扱わないでください |

## インストール

```bash
git clone https://github.com/Kurikara-dev/ifc-occam.git
cd ifc-occam
python -m venv .venv
```

仮想環境を有効化してから (Windows なら `.venv\Scripts\activate`)、

```bash
pip install -e .
```

テスト環境も入れるなら `.` の代わりに `".[dev]"` を指定して、`pytest` で確認できます。実データを使う統合テストが入っているので10分ほどかかります。

インストールが失敗する場合、原因はほぼ `ifcopenshell` です。プラットフォームと Python バージョンごとに別の wheel が配布されているので、その組み合わせが合っていないのが典型的なつまずきどころです。このプロジェクトは ifcopenshell 0.8.5 で開発しています。

仮想環境ができていれば、あとはコマンドを打たなくても動きます。**`start.bat` をダブルクリック**すれば GUI が起動します (`start-exe.bat` は `dist/` にある PyInstaller ビルドの exe を起動します。自分でビルドしたものでも、[Releases](https://github.com/Kurikara-dev/ifc-occam/releases) の Windows バイナリを `dist\ifc_occam\ifc_occam.exe` の形に展開したものでも動きます)。

非開発者向けには2つの文書があります。初めて触るなら、Releases の zip から始める [docs/quickstart.md](docs/quickstart.md) を先に読んでください。画面の細かい操作は [docs/testing-guide.md](docs/testing-guide.md) にあります。

## どのモードを使うか

| モデルサイズ | モード | 内容 |
|---|---|---|
| 〜300MB程度 | **GUI** | 3Dビューアで選択しながら、消す前に何が消えるか目で見て決める |
| 300MB〜2GB程度 | **CUI** | テキストスキャンでランキングを出し、クラス単位で決めてから1回だけフルオープンして出力 |
| それ以上、またはフルオープンがメモリに載らないとき | **CUI のテキストモード** (`--text`) | STEP のテキストを直接書き換えて削除する。モデルを一度も開かない |

真ん中の行の目安の根拠を書いておきます。`ifcopenshell` でモデルを開くと、**ファイルサイズの約14倍**のメモリを使います (実測して校正した係数です)。1.2GBのモデルでピーク14.75GBでした。CUI は適用前にこの推定値を出して、危なそうなときは警告します。

### GUI

```bash
python -m ifc_occam serve
```

表示された URL を開きます。モデルは**「ファイル指定」ボタンから開くファイル一覧ダイアログ**で選びます(サーバを起動したフォルダの中だけが見えます。パスが分かっていれば折りたたみ式の手打ち欄も使えます)。サイドバーは「クラス」「レイヤー」「重複形状」の3タブで、各行に要素数・形状数・三角形数が出て、マウスを乗せると削除/軽量化/残すのクイックボタンが現れます。ビューア上で要素をクリックして選ぶか、一覧の行でクラス/レイヤー単位でまとめて選び、削除、bbox化、OBB化(向き付きbbox)、凸包化、間引きのいずれかを設定します。名前を付けた**操作パターン**(クラス/レイヤー全体への操作をまとめたルール集で、適用前にルールごとの対象件数を確認できます)を保存・適用・削除できます。出力も**保存ダイアログ**から行い、読込中のファイルと同じ名前は選べません。3Dビューにはモデルの外形に合わせたグリッド付きの床が敷かれ、広がりと天地の目安になります(「ステージ」ボタンで表示切替可)、何か選ぶと非選択要素が暗くなり選択部分に縁取りが付きます。操作は右ドラッグで回転(カーソル直下の点が軸)、左ドラッグで見回し(カメラは動かず首を振るように視線だけ向きが変わります)、ホイールボタンのドラッグでパン、ホイールスクロールで拡大縮小、左クリックで選択です。配色は「IFCの色で表示する」と「クラス別に色分けする」を切り替えられます。ポート8000が使用中なら空きポートを自動で探して表示します。

どの手法を使うか迷ったときの目安です。

- **間引き**は三角形が密なメッシュに向きます。粗いメッシュ(部材あたりの三角形数が少ない)では、指定した率まで削れないことがあります
- **凸包**はくぼみのある(凹んだ)形状に向きます。もとからほぼ凸の形状には効果が小さいことがあります
- **OBB(向き付きbbox)/bbox**は部材が箱に近い形で十分なときに向きます。部材が座標軸に対して斜めなら、bboxよりOBBの方が形に沿います

間引きと凸包は三角形化して書き戻すため、三角形数が減ってもファイルサイズはむしろ増えることがあります。GUIとCUIはこの傾向に当てはまるとき、選択中のクラスと手法の組み合わせから操作を止めずに注意文を出します(サンプル実測に基づく参考情報で、判定できない場合は何も表示しません)。

![GUIの全体像。左にクラス別ランキング、右に3Dビュー](docs/images/gui-overview.png)

*読込直後。左のサイドバーで三角形数の多いクラスから順に並び、右の3Dビューはクラス別に色分けしています。*

![IfcWallを選択して間引きを積んだ状態。選択部分がオレンジと縁取りで示される](docs/images/gui-simplify.png)

### CUI

```bash
python -m ifc_occam cui heavy_steel.ifc
```

生の STEP テキストを軽くスキャンします。幾何エンジンは使わず、フルオープンもしません。数秒から数分でクラス別ランキングが出て、そのあと対話ループに入ります。

```
IFC Occam CUI — 軽量スキャン中...
=== クラス別ランキング (推定Face数[展開]降順) ===
...
操作を入力してください (h でヘルプ):
> delete IfcMechanicalFastener
> bbox IfcPlate
> list
> apply
```

コマンドは `delete`、`bbox`、`obb`、`hull`、`decimate`、`keep`、`undo`、`list`、`rank`、`apply` と、`help`、`quit` です。`apply` するまでディスクには何も書きません。`apply` は確認を2回取ります。1回目は操作サマリに対して、2回目は実ファイルを読んで削除の連鎖 (開口や充填要素) を展開したあとで、指定した以外に何件が一緒に消えるかを見せてから訊きます。出力ファイル名も訊きます。

軽量化系のコマンド (`bbox`/`obb`/`hull`/`decimate`) は既定で共有波及します。指定したクラスを軽量化すると、そのクラスが使っている共有形状を通じて、別クラスの要素の見た目も一緒に変わります (GUI の「共有波及」オプションと同じ挙動です)。確認2の画面では、選択していない要素が何件・どのクラスで変わるかも表示します。個別に効かせたいときは、コマンドの末尾に `element` を付けてください。

`--scan-only` を付けるとランキングを表示して終了します。初めて見るモデルの規模を測るならこれが速いです。

`--inline-cleanup` を付けると省メモリ方式で書き出します。既定では書き出し時に一括のゴミ回収を行い、そのとき一時的にモデルサイズの数倍のメモリを使いますが、この方式では簡略化のたびに古い形状を逐次回収します。GUI の「省メモリ方式で書き出す (逐次ゴミ回収)」チェックボックスと同じものです。生き残る要素と幾何、GlobalId は既定方式と同一で、同じ入力・同じ操作であれば出力は一括 GC とバイト単位で一致します。共有形状化 (consolidate) を ON にした場合も同様です (以前は共有先の代表選択が実行ごとに揺れて一致しませんでしたが、決定化済みです)。以前のリリースでは逐次回収が一括 GC ほど徹底せず出力が数%大きくなることがありましたが、その差は解消済みです。逐次回収のぶん掃除ステージは一括 GC より遅くなることがあります。モデルを開かないテキストモードには効きません。

### テキストモード: 開けないモデル向け

大きいだけでなく、要素ごとの編集自体が絶望的に遅いモデルがあります。実データのある系列では、`ifcopenshell` の要素単位の削除が**1要素あたり約22秒**かかりました。456要素で2.8時間です。同規模の別モデルでは110〜140ミリ秒でした。テキストモードはこういうモデルと、そもそも開けないサイズのモデルのために用意しました。

```bash
python -m ifc_occam cui huge_model.ifc --text
```

設定した操作が削除だけのとき、CUI は STEP ファイルをバイト列として書き換える経路を提案します。参照グラフをスキャンして、指定した要素と一緒に死ぬレコード (開口とその充填要素、集約された子部材、誰からも参照されなくなったレコード) を割り出し、生き残る関係レコードの参照リストからは死んだ参照だけを取り除き、それ以外はそのまま流します。`ifcopenshell` は一度も呼びません。

この提案が出るのは、操作が削除だけで、かつ `--text` を指定したか上記のメモリ警告が出ているときだけです。bbox や凸包や間引きは幾何生成が必要なので対象外です。正しさは等価性試験で固定しています。同じ削除をテキスト経路とフルオープン経路の両方で適用して、生存要素と幾何が一致することを確認します。この試験が**カバーしていない**範囲は[制約と既知の穴](#制約と既知の穴)に書きました。

## このツールがやらないこと

- **入力ファイルを書き換えません。** 出力先に入力ファイルを指定した場合は拒否して止まります
- **勝手に判断しません。** 自動最適化のようなものはなく、選択と確認と適用は必ず人間が行います
- **テキストモードではモデルを開きません。** それがこのモードの存在理由です

## 制約と既知の穴

以下は推定ではなく実測値です。

- **フルオープンはファイルサイズの約14倍のメモリを使います。** 2GBを超えたあたりで CUI が警告します。そこから先はテキストモードの領域です
- **テキストモードの参照グラフスキャンは、中間配列の削減後でファイルサイズの約1.6倍のメモリを使います**(1.2GBで実測1.63倍。参照が少なめの21.5MBモデルでは1.40倍で、係数は参照密度とともに上がります。旧実装は同じ21.5MBモデルで4.79倍でした)。**テキストモードは6.5GBで端から端まで検証済みです**。6.5GBモデルの全要素削除が32GB搭載機で27.4分で完走しました。参照グラフスキャン608秒 (11.4MB/s)、1億3,560万レコードを削除、出力は未解決参照ゼロで正常に開き直せ、元ファイルは無傷でした (SHA-256で確認)。正直に書いておくと、この検証モデルは関係レコードをほとんど含まない単一クラス構成のため、関係レコードの参照リスト修正の段はこの規模ではまだ本格的に動いていません。関係レコードの多い実務モデルでは計画段の処理時間が増えます
- **テキストモードは削除のみです**
- **テキストモードは残りかすを残し得ます。** カウントダウン方式の構造的な限界が2つ残っています(dead同士の循環参照は回収されない・パッチ候補の関係レコードを生存扱いする近似)。そのためレコード数がフルオープン経路と一致する保証はありませんが、アノテーションピン留め修正と残置回収の修正後、38万レコードのモデルで再実測したところ両経路の出力レコード数は完全に一致しました(差0レコード。修正前は+0.24%)。`IfcPresentationLayerWithStyle` による割り当てだけは今も既知の例外として残り、従来どおりピン留めします。生存要素と幾何はフルオープン経路と完全に一致します
- **テキストモードのカスケード等価性は合成データでしか検証できていません。** テストに使える実データに開口と充填要素が1件も入っていないため、開口の連鎖と集約の連鎖は専用に作ったフィクスチャで固定しています。どちらもフルオープン経路と完全一致しましたが、実物の建築モデルには当てていません
- **簡略化の掃除は書き出し時のスイープとして行われます。** 幾何を簡略化した出力では、出力ファイルの隣に一時ファイル `.gc-tmp`(ゴミ込みの「fat」ファイル。出力サイズではなく**入力モデルとほぼ同じ大きさ**)を作り、置き換え前の旧形状を消す参照グラフスキャン (テキストモードと同じスキャンです。以前は約4.8倍でした) のためにfatファイルの約1.6倍のメモリを一時的に必要とします。305MBのモデル(456要素)で実測したところ、このスイープ自体は約2分(119.9秒)でした(同モデルの20要素プローブでは79.8秒で、要素数への依存は弱い)。実行が強制終了された場合、出力の隣に `.gc-tmp` ファイルが残ることがあります(削除して構いません)
- **CI がカバーするのは合成フィクスチャのテストだけで、Windows のみです。** GitHub Actions で Windows のテストスイートを回していますが、実モデルの統合テストはリポジトリにデータが無いため CI では skip され、データを持つ環境でだけ走ります。Linux の CI も試しましたが、manylinux 版 `ifcopenshell` が幾何経路で segfault したため外しました (本プロジェクトのサポートは Windows のみ、という位置づけと整合します)。`v*` タグを push すると Windows 用バイナリが自動でビルドされます。実際に公開済みのものは [Releases](https://github.com/Kurikara-dev/ifc-occam/releases) を見てください

## 免責

出力ファイルは**参照用の派生物**です。設計や施工の正本として扱わないでください。出力からは要素が**不可逆に**削除・簡略化されています。元ファイルは変更しませんが、出力から消えた要素を元に戻すことはできません。設計と施工の判断は元ファイルで行ってください。

安全側の担保として、出力ファイルの IFC ヘッダには由来を刻印します。非正本であることの表示、元ファイル名、削除・簡略化した要素数を `FILE_DESCRIPTION.description` に追記します (`ViewDefinition` などの既存エントリは保持します)。あわせて `FILE_NAME.originating_system` も書き換えます。GUI と CUI のどちらでも、export のたびに自動で入ります。
